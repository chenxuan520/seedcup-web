# SeedCup Web 自动播放、机器人对齐与评测失真事故复盘

## 1. 文档目的

本文复盘 2026 年 7 月 31 日至 8 月 1 日 SeedCup Web 项目连续出现的自动播放失效、机器人行为偏离 C++、搜索增强强度结论失真、测试门禁缺失等问题。复盘的目的不是为单个代码错误寻找借口，而是把导致错误进入主分支、部署到 GitHub Pages、被用户反复发现的工程链路完整展开，并将整改要求变成仓库中的代码、测试、工作流和项目规则。

本次事故不是一个孤立的语法错误。它由四类问题叠加而成：

1. 模型异步加载完成后无条件重置游戏，覆盖了用户刚刚点击“开始”形成的运行状态。
2. 网页“困难”机器人没有严格对应比赛提交中的 C++ hard，而是错误复用了训练分支中加入动态方向序的实验配置。
3. 搜索增强的旧胜率来自非生产评测口径，评测器把地图 seed 注入 Bot 内部随机数，真实客户端和浏览器 Worker 并不会这样运行。
4. 离线 GameSim 的公平交错结算与原服务端“客户端动作谁先到就先应用”的竞争语义不同，较慢的搜索 Bot 在真实服务端上受到显著延迟惩罚。

如果只修复“点击开始不动”，后三类问题仍然会继续制造错误结论。如果只把搜索实现逐行移植，真实服务端的 timing race 仍然会让离线更强的策略在在线对战中失败。因此本次整改同时覆盖产品状态机、C++/JS 行为合同、评测统计、运行时并发语义和 CI 发布流程。

## 2. 项目背景与权威来源

SeedCup Web 是 2023 年种子杯炸弹人题目的浏览器机器人竞技场。用户可以选择手动、简单、困难、纯神经网络和搜索增强机器人，在浏览器里观看或参与 2 至 4 人对局。项目并不是重新发明规则，而是将下列已有实现迁移到浏览器：

- 官方服务端仓库：`chenxuan520/seedcup2023`。
- C++ SDK 与比赛 Bot 仓库：`chenxuan520/seedcup-cppsdk`。
- 比赛版 Bot 权威提交：`c7cdf9ee3ede1c7699ec7e6a9a72b1791b62f7af`。
- 训练出的纯神经网络模型：`pure-nn.rnn`。
- 训练分支上的 `RuleSearchBot` 与 DL+搜索 hybrid。

规则层的权威来源是官方 C++ 服务端。Bot 决策层必须区分两个来源：

- 用户可见 easy 和 hard 必须对应比赛提交 `c7cdf9e`。
- 搜索 teacher 的 baseline、rollout scorer 和训练实验来自训练分支当前代码。

这两个来源此前被错误混为一个“C++ hard”。训练分支为了训练和搜索实验，加入了运行时 `hard_mode`、`move_order_mode`、更严格的虚拟炸弹逃生判断、独立 `mt19937` 等机制。它们对于实验是合理的，但不能自动代表比赛时实际运行的 `./hard`。本次事故中最关键的认识之一，就是“来自同一个文件名”不等于“同一个行为合同”。

## 3. 用户可见事故

### 3.1 点击开始后页面不动

用户在神经网络模型仍在下载时点击“开始”，页面短暂进入运行状态。模型 Promise 完成后，成功回调和失败回调都调用 `resetGame()`。`resetGame()` 会把 `running` 设为 false、回合重置为 0、按钮文案改回“开始”。因此用户看到的现象是：刚点击开始，机器人却突然停止，像是按钮完全失效。

早期浏览器测试没有覆盖这个时序。测试总是先等待“神经网络模型已加载”，再点击开始，所以无法触发竞态。开发时手动操作也常在模型加载后开始，进一步掩盖了问题。

### 3.2 搜索增强在网页上打不过 hard

页面上已有“搜索增强”选项，文档又声称它比 hard 更强。实际线上代码却让 `search` 实例化纯 `SearchBot`，不加载 RNN prior；真正的 `HybridSearchBot` 只存在于另一个 `hybrid` 选项中。用户看到的名称和执行的 Bot 不是同一个版本。

更严重的是，即使把 `search` 切到 `HybridSearchBot`，旧的“65.2% 胜率”也不能直接成立。旧结论来自错误评测口径和错误 hard 对手。修复后必须重新测量，而不能把历史数字当成产品承诺。

### 3.3 easy、hard 与多人局行为被质疑

用户在四人局观察到机器人卡位、相互不走、easy 自炸等现象，要求所有规则与 C++ 完全一致。此前实现虽然做过若干单步 fixture，但 fixture 范围有限，且没有清楚区分：

- 比赛版 easy。
- 比赛版 hard。
- 训练分支 hard。
- 搜索内部 rollout rule opponent。

当这些角色共用一个 `RuleBot` 构造参数时，修改一个方向序或放弹安全判断可能同时改变多个角色。没有独立合同和独立 fixture，就无法回答“这个 hard 到底是哪一个 hard”。

### 3.4 发布后才发现功能回归

原 GitHub Pages 工作流只执行 `npm ci` 和 `npm run build`，不运行单元测试、C++ 对拍、覆盖率或 Playwright。只要 TypeScript 能编译，代码就会直接部署。角色图标改动虽然表面上只涉及 UI，但同一提交上下文中的运行状态问题没有被发布门禁拦截。用户收到失败邮件和线上不可玩结果，说明发布流程没有提供应有的保护。

## 4. 时间线

### 4.1 初始移植阶段

网页端先实现地图、道具、角色、Bot 选择和基础自动播放。为了让多个机器人不阻塞主线程，Bot 决策放入独立 Web Worker。服务端状态序列化后广播给各 Worker，Worker 基于同一回合快照生成完整动作批次。

这个阶段主要验证“能运行”，没有建立生产 `src` 的覆盖率门禁，也没有把 GitHub Pages 部署依赖于测试 job。C++ fixture 以 easy、NN 单帧和部分服务端场景为主，hard 与搜索的完整对局覆盖不足。

### 4.2 easy 对齐与道具权重调整

用户要求 easy 与比赛 C++ 完全一致，随后锁定 `c7cdf9e` 历史提交作为权威来源。两人 47 步和四人 236 步 easy fixture 最终做到动作 0 分歧。与此同时，官方服务端和 Web 将无敌道具权重从旧袋中的 `1/23` 降到新袋中的 `1/45`，其他道具相对比例保持不变。

但是 C++ 训练 GameSim 的道具袋当时仍保留旧权重，形成裁判漂移。后续通过 60 张 seed 1000 至 1059 地图 fixture 才发现并同步。

### 4.3 角色图标改动与自动播放事故

角色图标提交部署后，用户反馈“点击开始都不动”。第一轮检查在线页面时，在模型已经加载完成的条件下点击开始可以推进回合，容易得出“无法复现”的错误结论。进一步构造网络延迟后才复现：

1. 页面初始化，开始下载模型。
2. 用户提前点击开始。
3. 回合开始推进。
4. 模型下载完成。
5. Promise 回调执行 `resetGame()`。
6. 运行状态被清除。

修复是删除模型加载成功和失败回调中的 `resetGame()`。模型是否可用只更新模型状态，不再重置正在进行的对局。新增 Playwright 专项用例在模型加载前点击开始，并验证加载完成后回合继续推进，同时覆盖暂停、继续、调速、重开和单步。

### 4.4 搜索增强强度复查

最初引用的 C++ hybrid 结果是 paired 250 seeds、500 局中 326 胜，即 65.2%。Web 端固定 120 局只有 64 胜，即 53.33%。差距达到 11.87 个百分点，不能归因于普通抽样噪声。

第一轮逐步对拍发现，给定完全相同的 C++ `GameMsg` 状态时，Web 搜索的 hard baseline、六动作 rollout 分数、RNN prior、最终动作和炸弹 tracker 都可以逐项一致。差异不在评分公式本身，而在整局状态演进、容器迭代顺序和评测随机数。

随后新增正反手整局导出器与 checker，逐回合比较双方动作、搜索每个 substep 的 baseline/chosen/六分数/tracker，以及结算后的完整状态。这个过程暴露了以下差异：

- C++ `unordered_map` 的玩家迭代顺序与 JS 数组顺序不同。
- `DeepCopyGameMsg` 会重新插入 unordered_map，可能再次改变顺序。
- 客户端规划时创建的虚拟炸弹 ID 公式不同。
- C++ 搜索 rollout 对手切到比赛 hard 后，JS 内部仍使用训练 hard。
- C++ 同进程评测中多个 Bot 曾共享全局随机状态，而真实客户端是独立进程。

这些差异逐项修复后，seed 43 的搜索先手 100 回合和搜索后手 62 回合整局对拍全部通过。

### 4.5 hard 合同错误被确认

网页“困难”曾使用 `RuleBot(true, 4)`。mode 4 是训练分支后来加入的动态方向序实验配置，不是比赛 `./hard`。

继续比较 `c7cdf9e:src/bot.h` 与当前训练分支后发现，差异不止方向序：

- 比赛 hard 每次 `CalcOnce` 都调用 glibc `random_shuffle`。
- 比赛 hard 与 easy 共享原始 `CanPleaceBomb` BFS，只是 hard 在目标筛选时使用安全判定。
- 训练 hard 使用独立 `mt19937`，且只在安全态洗牌。
- 训练 hard 的放弹逃生使用虚拟炸弹集合和更严格的路径判断。
- 训练 hard 的手套 BFS 增加 visited guard，比赛版没有。

因此简单把 order mode 从 4 改成 0 仍然不等于比赛 hard。最终新增 `ContestHardBot`，显式实现比赛合同；C++ 当前分支新增 `contest_rules`，`./hard` 默认开启。以历史 c7 头文件、`-DHARD` 编译生成的 seed 42 fixture 共 217 个连续动作，JS 动作分歧为 0；当前 C++ contest 模式与历史 fixture 也为 217 步、动作分歧 0。

### 4.6 真实服务端结果推翻离线结论

修复语义后，搜索增强在 C++ GameSim 的配对评测中仍可取得正收益。加入可见地图派生的稳定 RNG 后，depth 3、rollout 1 对训练分支 hard 的 500 局结果曾达到 288 胜、211 负、1 平，胜率 57.6%，Wilson 95% 区间为 53.2% 至 61.9%。

然而真实官方服务端按客户端动作消息到达顺序立即应用动作。搜索 Bot 每回合执行多个 rollout，MapCall 实测平均约 10 至 14 毫秒，p95 可超过 25 毫秒；hard 通常在微秒级完成。即使两者都没有错过 80 毫秒 tick，hard 也会稳定更早提交。

在固定 seed 20260801 至 20260805、每个 seed 交换连接顺序的 10 局真实服务端配对中，搜索增强最终 2 胜 8 负，无超时、无缺失结果。这个数据直接否定“当前搜索增强在真实服务端稳定强于 hard”的表述。

## 5. 根因分析

## 5.1 根因一：异步生命周期与游戏状态缺少所有权边界

模型加载属于资源生命周期，对局运行属于游戏状态机。原实现把两者通过 `resetGame()` 直接耦合，等价于允许一个较晚完成的资源请求覆盖用户已经执行的命令。

正确边界应为：

- 模型加载只更新 `nnPolicy`、状态文本和可用性标识。
- 对局创建、暂停、继续、重置只由用户命令或导入流程触发。
- Worker 重配使用 generation/token 丢弃旧回复，不重置新的用户状态。

此次错误之所以进入线上，是因为测试只覆盖“资源先完成、用户后操作”的常规顺序，没有覆盖“用户先操作、资源后完成”的逆序。

## 5.2 根因二：以类名和构造参数代替行为合同

`RuleBot(true, 4)`、`RuleBot(true, 0)`、历史 `-DHARD`、训练分支 `hard_mode=true` 都可以被口头称作 hard，但行为不同。工程上没有建立独立命名和 fixture，导致实验参数被当成官方实现。

整改后的合同为：

- `RuleBot(false, 0)`：比赛 easy。
- `ContestHardBot`：比赛 c7 hard。
- `RuleBot(true, 4)`：训练分支动态方向序 hard，仅用于搜索 self baseline。
- `HybridSearchBot`：训练分支 baseline + 比赛 hard rollout opponent + RNN prior。

只有明确的类型和 fixture 才能让代码审查者知道修改影响哪个角色。

## 5.3 根因三：评测器改变了被评测策略

旧 C++ `rule_search_oracle_eval` 为了让多线程分片可复现，在每局开始时执行：

```text
ResetMoveShuffleRngForThread(map_seed ^ constant)
```

真实 `dl_bot` 进程不会知道服务端隐藏 seed，也不会把它注入方向 RNG。浏览器 Worker 同样从固定默认种子启动。评测器因此不是“控制噪声”，而是改变了策略：不同地图获得不同方向序列，而生产中每局从同一方向随机状态开始。

同一批 60 个 seed 的证据非常直接：

- 旧 map-seeded C++ hybrid：76 胜、44 负，63.33%。
- 生产默认 RNG C++ hybrid：62 胜、58 负，51.67%。
- 修复后 Web hybrid：63 胜、57 负，52.5%。

Web 与生产 C++ 只差 1 局，旧评测器却高出十多个百分点。旧“65.2%”不能继续作为生产强度证据。

整改后评测输出必须显式报告：

- `production_move_rng`。
- `map_seeded_move_rng`。
- 对手合同。
- depth、rollouts、min gap、policy prior。
- paired sides 与 seed 范围。

## 5.4 根因四：模拟器公平结算与真实服务端竞争语义不同

C++ GameSim 为了避免永久先手偏置，按 substep 交错执行双方动作，并逐回合反转先执行者。真实官方服务端则在网络层收到某个客户端动作消息后立即调用 `Game::AddAction`，先到消息先改变状态。

这意味着算法延迟不仅影响是否错过 tick，还影响同一回合冲突的结算顺序。过去只检查“MapCall 小于 80ms”，认为没有 missed tick 就安全，这是错误的。即使搜索耗时 10ms，hard 耗时几十微秒，hard 也能在绝大多数回合先提交。

真实 server 的 2:8 结果说明，离线 55% 至 60% 的策略优势不足以抵消先到竞争。除非：

- server 改为收齐同轮动作后公平交错结算；或
- 搜索降到与 hard 同量级的微秒延迟；或
- 搜索优势大到足以覆盖系统性后手惩罚。

当前三者都没有满足。

## 5.5 根因五：测试和发布门禁缺失

原 Pages workflow 只构建不测试。项目没有统一覆盖率工具，早期还尝试过 c8、nyc、V8 与 Istanbul 手工合并，因文件 ID 不一致无法形成可信数字。

最终统一使用 Vitest Istanbul，unit project 与 Chromium browser project 共同采集生产 `src/**/*.ts`，四项全局阈值分别为 90%。当前结果：

- Statements：97.40%。
- Branches：90.72%。
- Functions：98.56%。
- Lines：98.76%。

GitHub Pages workflow 现在分成 `test` 和 `deploy` 两个 job。`deploy` 必须 `needs: test`，只有完整 `npm run ci` 成功后才会上传页面。

## 6. 修复设计

### 6.1 自动播放状态机

删除模型加载回调中的 `resetGame()`。新增 `autoplay-check.ts`，通过延迟模型响应构造竞态：

1. 页面加载后模型仍未完成。
2. 点击开始。
3. 回合从 0 推进到 1。
4. 模型加载完成。
5. 回合继续推进，不被重置。
6. 验证暂停后回合不变。
7. 验证继续后回合增加。
8. 验证速度调整改变推进量。
9. 验证重开回到 0。
10. 验证单步精确增加 1。

### 6.2 Worker generation 与错误处理

每次重配 Worker 增加 generation；每回合增加 round token。旧 generation 或旧 round token 的回复直接丢弃，避免旧 Worker 在重开后修改新对局。

`BotWorkerClient` 新增 `readySettled`。初始化期 error 才 reject ready promise；ready 后的运行期 error 只 reject pending decision。这样既避免未处理 Promise rejection，也保留错误提示和回合继续能力。

### 6.3 C++ 容器顺序移植

C++ `unordered_map`/`unordered_set` 的迭代顺序会影响：

- 首个敌人的选择。
- 炸弹同时爆炸时 owner 计分顺序。
- rollout 中双方执行顺序。
- DeepCopy 后的玩家/炸弹迭代。

Web 端加入 GCC 8 bucket count、rehash 与同 bucket 插入顺序模拟。玩家主座位顺序与 C++ GameMsg 迭代顺序分开保存，避免为了模拟容器顺序破坏 UI 颜色和座位。

### 6.4 虚拟炸弹语义

C++ Bot 本地规划的虚拟炸弹 ID 为：

```text
INT32_MAX - bombs.size() - 1
```

Web 原来使用负数 ID，导致炸弹 tracker 与 DeepCopy 容器顺序不同。现已改成同一公式。比赛 c7 的虚拟炸弹 `bomb_status` 未初始化，紧凑状态 hash 对大于 20 亿的虚拟炸弹不比较 status，但真实服务端炸弹仍严格比较剩余时间。

### 6.5 比赛 hard 独立随机状态

历史比赛 Bot 使用进程全局 glibc `random_shuffle`。真实部署中每个 Bot 是独立进程，因此每个客户端拥有独立随机状态。in-process 评测如果让多个 Bot 共享全局 `rand()`，搜索内部 rollout 会推进真实 hard 的随机序列，制造不存在于部署环境的数据竞争。

C++ 当前分支为 contest rules 使用 `random_r` 实例状态；每个 Bot 构造和 Reset 时以 seed 1 初始化。算法输出与历史 c7 的 glibc shuffle 相同，但不同 Bot 实例互不污染。JS 使用兼容的 `GlibcRand`，每个 Worker/实例独立保存。

### 6.6 搜索参数与地图派生 RNG

搜索对六个动作逐一做 rollout：

```text
hard baseline
  -> 六动作合法性检查
  -> 每个动作 depth 轮模拟
  -> 启发式状态评分
  -> 加 0.005 * RNN policy prior
  -> 仅当原始 rollout 分数超过 baseline 至少 minGap 才覆盖
```

生产默认从 depth 6、rollout 2 调整为 depth 3、rollout 1，减少约四分之三模拟轮数。地图派生 RNG 使用可见地图结构和出生点计算 FNV-1a 32 位 hash，不使用服务端隐藏 seed。这样不同地图获得稳定不同的 rollout 方向序列，同时 C++ 与 JS 可完全复现。

### 6.7 并行评分实验

六个动作理论上可并行。实验版本使用 `std::async`：

- 单线程更新 bomb tracker。
- 快照 RNG。
- 每个动作 clone 独立 scorer 和 GameMsg。
- 六个 future 并发计算。
- 汇总时保持动作索引顺序。

正确性验证在 112 个连续动作上得到：

- action 分歧 0。
- 六动作 score 分歧 0。
- prior 分歧 0。
- tracker 分歧 0。

但性能验证失败：

- 串行同 fixture：744ms。
- `std::async` 并行：1263ms。
- 真实 server 串行 p50：约 8.6ms。
- 真实 server并行 p50：约 12.5ms。

线程创建和 scorer 深拷贝成本超过并行收益。因此默认关闭，只保留 `--rs-parallel-scoring` 作为可复现实验。后续若继续并行，必须采用持久线程池和预分配 scorer，不能每次动作创建线程。

## 7. 测试体系

### 7.1 规则单元测试

覆盖：

- RNG 与 C++ `mt19937`/glibc rand 一致性。
- 序列化与 legacy 可选字段。
- 放弹、移动、碰撞、道具、护盾、无敌和回血。
- 推弹、链式爆炸、泥块隐藏道具。
- 胜负、平局、分数比较。
- speed 多动作额度。
- GameSim 与 server 两套裁判边界。

### 7.2 Bot 单元测试

覆盖：

- easy/hard 的速度差异。
- 四种训练方向序。
- 危险逃生、无敌碰撞危险、手套推弹。
- 搜索非法动作、危险态不搜索、无对手。
- 纯 NN 无模型、合法 fallback。
- hybrid 的 RNN prior 和 history commit。
- Worker configure/ready/decide/error/stale generation/dead player。

### 7.3 C++ fixture 对拍

当前门禁包括：

- 官方 server 地图生成。
- server 规则场景。
- server 四人场景。
- C++ GameSim 60 张地图。
- NN 单帧全部特征与概率。
- NN 40 步 RNN history。
- easy 两人 47 步。
- easy 四人 236 步。
- 比赛 hard 217 步。
- rule search 112 步六动作评分。
- hybrid search 112 步六动作评分与 prior。
- hybrid vs contest hard 正反手 100/62 回合完整状态摘要。

所有动作对拍要求 0 分歧；搜索 score 要求误差不超过 `1e-12`，RNN prior 只允许浮点舍入级 `1e-9`。

### 7.4 Browser Mode 与 Playwright

Browser Mode 覆盖真实 `main.ts`、真实 Worker、模型加载、导入导出、Canvas 所有道具和状态、胜负 overlay、legacy 存档迁移、模型 404 和 Worker 错误。

Playwright 外部回归覆盖：

- 2 人和 4 人对局。
- 随机地图与固定 seed 重现。
- 自动播放提前点击竞态。
- 开始、暂停、继续、单步、重开和调速。
- 爆炸视觉效果。
- 设置面板和帮助弹窗。
- Worker 数量和到达记录。

### 7.5 CI 与部署

`npm run ci` 顺序执行：

1. Vitest Istanbul 全覆盖率。
2. 生产构建。
3. C++/JS 全部 fixture 对拍。
4. Bot speed 与长局自测。
5. Playwright 浏览器回归。

GitHub Pages 只有在 `test` job 成功后才执行 `deploy`。失败测试不会部署，也不会产生“构建成功但功能坏了”的页面。

## 8. 评测数据与结论

### 8.1 纯 NN

纯 NN 模型对 easy 有明显优势，但对 hard 没有达到稳定持平。此前严格审计约为 24% 至 28%，说明模型单独运行时缺少前向规划能力。这个结论没有因为搜索修复而改变。

### 8.2 搜索的离线能力

在训练分支 GameSim 的公平交错语义下，地图派生 RNG 和浅层搜索能提供正收益。不同 hard 合同和 RNG 口径会得到不同数字，因此任何胜率必须同时报告完整配置。

目前最重要的不是某一个百分比，而是已经确认：

- 固定生产 RNG时，旧 hybrid 约为五五开。
- 地图派生 RNG可让离线胜率提高。
- depth 3/rollout 1 的成本和胜率优于旧 depth 6/rollout 2 的部分口径。
- 错把训练 mode 4 当比赛 hard 会改变结果。

### 8.3 真实服务端

最终固定 seed 真实服务端配对：

```text
seeds: 20260801..20260805
每个 seed 两局，交换连接顺序
game_max_round: 300
tick: 80ms
搜索增强: depth=3, rollouts=1, minGap=0.05, policyPrior=0.005
结果: 2 胜 8 负，0 error
```

因此本项目当前不能声称“搜索增强在原服务端稳定击败 hard”。网页仍可保留“搜索增强”名称，表达它在规则 baseline 上增加了前向模拟和 RNN prior；但文档必须注明它是算法演示，不是已验证的真实服最强机器人。

## 9. 为什么之前会给出错误结论

错误结论不是一次算术失误，而是评测对象和运行环境被悄悄替换：

1. 对手从比赛 hard 换成训练 mode 4 hard。
2. Bot 内部 RNG从生产固定种子换成地图 seed。
3. 裁判从真实 server 先到竞争换成 GameSim 公平交错。
4. 网页 `search` 还一度没有加载 hybrid prior。

每一步单独看都像合理工程选择，组合后却形成一个只在评测器中存在的策略。旧 65.2% 测量的是“训练 hard + map-seeded RNG + GameSim 交错”的 hybrid，不是网页用户点击的 Bot，也不是原服务端上运行的客户端。

## 10. 工程责任与流程缺陷

### 10.1 没有先定义验收合同

“完全对齐 C++”必须先回答：

- 哪个仓库？
- 哪个 commit？
- 哪个编译宏？
- 哪个运行参数？
- 一个进程还是多个进程？
- RNG 是否独立？
- 服务端如何结算并发动作？

此前直接从当前训练分支抄代码，没有把这些问题写成合同，导致后续反复返工。

### 10.2 测试围绕实现写，而不是围绕事故写

最初 E2E 等模型加载完再点击开始，验证的是实现最顺利的路径。正确做法应从用户事故反推时序：在模型未完成时点击开始。类似地，search 单步 fixture只覆盖先手一条轨迹，没有覆盖后手和完整胜负。

### 10.3 把“测试通过”误当“测试充分”

单步 score 0 分歧不能证明整局一致；整局一致不能证明对手合同正确；离线胜率不能证明真实 server 强。测试需要分层回答不同问题，不能让一个绿色结果承担它没有覆盖的结论。

### 10.4 发布工作流没有质量门禁

任何项目只 build 不 test 的 Pages workflow 都等于把用户当回归测试。此次整改把部署依赖测试 job，并在 `AGENTS.md` 中要求每次提交前独立 review。

## 11. 防再发规则

### 11.1 修改 Bot 前

必须写清：

- 修改哪个行为合同。
- 权威 C++ 文件与 commit。
- 是否影响 easy、contest hard、training hard、search self 或 rollout opponent。
- RNG 和进程隔离语义。

### 11.2 修改 Bot 后

至少运行：

- 对应 C++ 单步 fixture。
- 一条正手整局。
- 一条反手整局。
- 覆盖率。
- 浏览器真实 Worker 回归。

若声称强度提升，还必须运行 paired sides 多 seed，并区分离线与真实 server。

### 11.3 提交前

必须：

- `git diff --check`。
- `npm run ci`。
- C++ 全量构建。
- 独立 code review agent 审查代码。
- 修复 reviewer 阻塞问题后重新审查。

### 11.4 发布后

必须：

- 等 GitHub Actions test 与 deploy 都成功。
- 在线页面确认模型加载。
- 在模型未完成时提前点击开始。
- 验证回合推进、暂停、继续、重开。
- 验证 hard 与 search 实际 Worker 创建。
- 检查控制台无 error。

## 12. 剩余风险

### 12.1 比赛 hard 手套 BFS 性能

比赛 c7 的 `GetClosestMoveBomb` 不在普通分支入队时标 visited。特定地图和手套状态下，队列可能指数膨胀。为了完全对齐比赛行为，网页 `ContestHardBot` 保留该逻辑。测试和评测必须设置 wall-clock 防护，不能直接用高并发跑大量比赛 hard 局。

### 12.2 搜索真实服务端延迟

depth 3/rollout 1 仍比 hard 慢几个数量级。临时线程并行已经证明负收益。可行的后续路线包括：

- 常驻线程池。
- 预分配 6 个 scorer。
- 将候选评分并入单一批量模拟器，减少 DeepCopy。
- 缓存同一回合公共 rollout 前缀。
- 将搜索放在上一回合后台预计算，但需要处理状态失配。

任何优化都必须保持 score fixture 逐位一致。

### 12.3 Web Worker 到达竞争

网页按 Worker Promise 完成顺序应用完整动作批次，与原服务端先到语义一致。这会让计算更慢的搜索 Bot系统性后到。若产品目标是“公平展示算法强度”，可以新增明确的“公平同步模式”；但不能静默替换默认服务端语义。两种模式必须在 UI 和文档中区分。

### 12.4 多人搜索

当前 SearchBot rollout scorer主要按一对一 opponent 建模。网页可在多人局运行，但不能宣称多人强度等同一对一。多人搜索需要显式选择所有对手或建联合策略，而不是只取第一个敌人。

## 13. 后续路线

### 13.1 短期

1. 发布本次状态机、hard 合同、fixture、覆盖率和 CI 修复。
2. 页面文案明确搜索增强是实验策略。
3. 保留纯 NN 供展示训练成果。
4. 保留真实 server 配对脚本，不放入每次 push CI。

### 13.2 中期

1. 为搜索实现持久线程池。
2. 将六动作评分改成批量 GameSim。
3. 在相同固定 seed paired server 合同下比较延迟与胜率。
4. 若真实 server仍低于 hard，停止宣传强度，转为教学演示。

### 13.3 长期

1. 若允许修改 server，增加收齐同轮动作后的公平结算模式。
2. 用更强搜索产生训练数据，训练 value/policy 网络减少在线 rollout。
3. 建立离线 teacher 强度、蒸馏准确率和真实 server胜率三套独立指标。
4. 对任何“更强”声明要求置信区间与复现脚本。

## 14. 最终结论

本次工作真正完成的不是“把一个按钮修好”，而是纠正了项目对行为一致性和强度评测的理解：

- 自动播放竞态已修复，并有逆序时序测试。
- easy 与比赛 c7 C++ 两人/四人动作严格一致。
- hard 与比赛 c7 C++ 217 步动作严格一致。
- search/hybrid 单步六动作评分严格一致。
- search 对 contest hard 正反手整局严格一致。
- C++ GameSim 道具袋与新 server 权重一致。
- 生产源代码四项覆盖率全部超过 90%。
- Pages 部署受完整测试门禁保护。
- 旧 65.2% 强度结论被判定为非生产口径，不能继续使用。
- 当前搜索增强在真实原服务端固定 seed 配对中为 2 胜 8 负，尚未打败 hard。

最重要的工程教训是：一致性必须由明确的 commit、编译宏、随机状态和并发语义共同定义；强度必须在实际部署裁判上测量；测试必须覆盖用户触发事故的时序，而不是只覆盖开发者最熟悉的顺序。任何缺少这些条件的“已经对齐”“已经更强”“测试没问题”都不是可审计的技术结论。
